# لانچ‌اوکس

فروشگاه آنلاین فارسی با Next.js، TypeScript و Tailwind CSS. پروژه مطابق بخش ۱۲ از [مشخصات](docs/SPEC.md) در دوازده مرحله ساخته می‌شود؛ مراحل اول تا نهم، شامل فروشگاه، سبد خرید، تسویه‌حساب و پرداخت آزمایشی پیاده‌سازی شده‌اند.

## پیش‌نیازها

- Node.js نسخهٔ 24 LTS و npm (برای سازگاری با ابزارهای جدید)
- Docker Desktop با موتور کانتینرهای Linux برای MongoDB محلی

## راه‌اندازی

```sh
npm install
```

اگر `.env.local` ندارید، `.env.example` را در آن کپی کنید. فایل موجود را بازنویسی نکنید. برای احراز هویت، مقدار نمونهٔ `AUTH_SECRET` را با یک مقدار تصادفی امن و رمز نمونهٔ ادمین را با رمز شخصی جایگزین کنید.

```sh
npm run db:up
npm run seed
npm run dev
```

صفحهٔ آغازین در <http://localhost:3000> نمایش داده می‌شود. MongoDB نسخهٔ ۷ روی پورت ۲۷۰۱۷ اجرا می‌شود و داده‌های آن در volume نام‌دار `mongo_data` باقی می‌ماند. برای استفاده از Atlas، مقدار `MONGODB_URI` را تغییر دهید. مسیر `/api/health` اتصال واقعی دیتابیس را با ping بررسی می‌کند.

تنظیمات الزامی در `src/lib/env.ts` با Zod بررسی می‌شوند؛ اگر فایل محیطی قدیمی فقط بخشی از کلیدها را دارد، کلیدهای گمشدهٔ `.env.example` را اضافه کنید و مقادیر موجود را حفظ کنید. `AUTH_URL` در production الزامی است و تنظیمات seed برای برنامه اختیاری‌اند، اما اجرای seed به ایمیل و رمز ادمین نیاز دارد. پیام تنظیم نامعتبر نام کلید را نشان می‌دهد و مقدار آن را افشا نمی‌کند.

در PowerShell با محدودیت اجرای اسکریپت، از `npm.cmd` به‌جای `npm` استفاده کنید.

## دستورها

| دستور               | کاربرد                                         |
| ------------------- | ---------------------------------------------- |
| `npm run dev`       | اجرای توسعه با Turbopack                       |
| `npm run build`     | ساخت نسخهٔ production                          |
| `npm start`         | اجرای نسخهٔ ساخته‌شده                          |
| `npm run lint`      | بررسی ESLint                                   |
| `npm run typecheck` | بررسی TypeScript                               |
| `npm run test`      | اجرای Vitest                                   |
| `npm run format`    | فرمت با Prettier و مرتب‌سازی کلاس‌های Tailwind |
| `npm run db:up`     | اجرای MongoDB محلی                             |
| `npm run seed`      | ساخت یا به‌روزرسانی دادهٔ نمونه                |

## دادهٔ نمونه

با `npm run seed` پنج دسته، ۲۴ محصول، ادمین با تنظیمات `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` و مشتری `customer@launchox.local` / `Customer123!` با آدرس تهران ساخته می‌شوند. اجرای مجدد با ایمیل و نامک upsert می‌کند. `npm run seed -- --reset` محصولات، دسته‌ها، سبدها، سفارش‌ها و شمارنده‌ها را پاک می‌کند؛ کاربران حفظ می‌شوند. در production فقط با `--force` اجرا می‌شود. خلاصهٔ تعدادها و اطلاعات ورود ادمین در پایان چاپ می‌شود؛ این خروجی را منتشر نکنید.

## ساختار فعلی

- `src/app/`: فروشگاه فارسی و RTL، کاتالوگ و سبد، فرم‌های ورود و ثبت‌نام، checkout، درگاه آزمایشی و نتیجهٔ پرداخت؛ حساب و ادمین فعلاً نقاط ورود محافظت‌شده‌اند
- `src/components/ui/`: کامپوننت‌های پایهٔ Button، Input، Card و Badge
- `src/lib/`: ابزارهای فرمت فارسی، slug، ترکیب کلاس‌ها، تنظیمات محیطی، اتصال MongoDB و خطاهای برنامه
- `src/models/`: مدل‌های User، Category، Product، Cart، Order و Counter با ایندکس‌ها و timestamps
- `src/types/`: نوع‌های مشترک و DTOهای قابل ارسال به کلاینت؛ شناسه‌ها و تاریخ‌ها رشته‌اند و passwordHash در DTO وجود ندارد
- `src/validations/`: اسکیماهای Zod برای auth، product، category، address، cart، order و ورودی‌های مشترک
- `src/lib/model-shared.ts`: تعریف آدرس، قواعد مشترک مدل‌ها و تبدیل بازگشتی `toDTO` برای رکوردهای lean و `toJSON`
- `src/services/health.service.ts`: بررسی وضعیت دیتابیس؛ `auth.service.ts`: اعتبارسنجی، خواندن امن کاربر و ثبت‌نام مشتری با bcrypt
- `src/services/order.service.ts`: محاسبات مبالغ، رزرو موجودی، سفارش، تغییر وضعیت و انقضا؛ `payment/`: interface، fake، callback و stub درگاه واقعی؛ `user.service.ts`: آدرس‌های checkout
- `src/actions/checkout.actions.ts` و `src/app/api/payment/callback/route.ts`: ثبت سفارش، افزودن آدرس و بازگشت از درگاه با کنترل مالکیت
- `src/app/api/health/route.ts`: پاسخ JSON پویا و بدون کش برای وضعیت سلامت
- `tests/`: تست‌های format، slug، env، db، health، errors، اعتبارسنجی، مدل‌ها، سرویس احراز هویت، محافظ‌ها، proxy و rate limit؛ `auth-browser.py` برای پذیرش واقعی مرورگری
- `public/`: تصاویر استاتیک قالب اولیه
- `vitest.config.mts`: تنظیمات تست و مسیر مستعار `@/`
- `docker-compose.yml`: دیتابیس محلی
- `AGENTS.md` و `docs/SPEC.md`: قوانین و مشخصات پروژه

صفحات کامل حساب مشتری و پنل ادمین به‌ترتیب در مراحل ۱۰ و ۱۱ ساخته خواهند شد. درگاه آزمایشی فقط در توسعه و تست فعال است؛ در production ثبت پرداخت آزمایشی پیش از رزرو موجودی رد می‌شود.

تست مدل‌ها یک MongoDB 7 جداگانه با `mongodb-memory-server` می‌سازد و داده‌های آن را بین تست‌ها پاک می‌کند. اگر باینری قابل دریافت یا اجرا نباشد، یک کانتینر موقت `mongo:7` با پورت تصادفی روی localhost و داده‌های tmpfs ساخته و در پایان حذف می‌شود؛ در این حالت Docker Desktop باید روشن باشد. هیچ‌یک از این مسیرها از `MONGODB_URI` پروژه استفاده نمی‌کنند. نخستین اجرای تست ممکن است برای دانلود باینری یا image به اینترنت نیاز داشته باشد.

## Decisions

- مرحلهٔ نهم: ثبت سفارش روی MongoDB مستقل نیز کار می‌کند؛ رزرو اقلام اتمیک و شکست‌ها با بازگرداندن موجودی جبران می‌شوند. قفل سبد مانع checkout تکراری است و ویرایش هم‌زمان سبد باعث rollback می‌شود. callback با مالک سفارش محدود و تغییر پرداخت با شرط وضعیت قبلی انجام می‌شود تا callback تکراری موجودی و soldCount را دوباره تغییر ندهد.
- افزودن و انتخاب آدرس فقط داخل checkout اضافه شده؛ صفحات حساب مرحلهٔ دهم ساخته نشده‌اند. آدرس جدید پیش‌فرض موجود را تغییر نمی‌دهد. خطای stub درگاه واقعی برای رعایت AGENTS.md فارسی است؛ fake در production پیش از رزرو سفارش رد می‌شود.
- تست مرورگری مرحلهٔ نهم: روی دیتابیس موقت seedشده اجرا شود؛ `LAUNCHO_CHECKOUT_TEST_DB` باید URI دیتابیس مستقل با نام `launchox_stage9_browser` باشد و `LAUNCHO_CHECKOUT_TEST_URL` آدرس سرور توسعهٔ همان دیتابیس است. دستور `python tests/checkout-browser.py` مسیر خرید، انصراف، مالکیت، callback تکراری و RTL/تم/عرض‌ها را بررسی می‌کند.

- مرحلهٔ هشتم: جمع مبالغ و ارسال سبد فقط در بخش محاسبات `order.service.ts` انجام می‌شود؛ هیچ منطق ثبت سفارش یا پرداخت اضافه نشده است. شمارنده مجموع تعداد واحدهای قابل‌خرید است. خواندن سبد اقلام نامعتبر را کنار می‌گذارد و کاهش موجودی را با هشدار نمایش می‌دهد، بدون بازنویسی هم‌زمان دادهٔ سبد. هدر برای خواندن کوکی و شمارنده پویا است. کنترل تعداد با انتخاب‌گر محدود به موجودی و ۱۰ انجام می‌شود؛ افزودن تعداد اضافی در سرور نیز محدود می‌شود.

- مرحلهٔ هفتم: محتوای سه اسلاید Hero به‌صورت دادهٔ نمایشی قابل‌تعویض داخل کامپوننت نگه داشته شد؛ چون SPEC مدل Hero ندارد، مدل یا پنل مدیریتی تازه‌ای اضافه نشد. دو تصویر روشن و تیرهٔ اصلی به‌طور اختصاصی از زبان بصری مراجع ساخته و داخل `public/images` نگه‌داری می‌شوند.
- کاتالوگ seed با حفظ نامک‌ها، شناسه‌ها و قرارداد ۵ دسته/۲۴ محصول به فروشگاه تخصصی سرمایش تبدیل شد تا اجرای عادی seed رکوردهای موجود را درجا به‌روزرسانی کند. کارت‌ها تصویر محلی امن یا URL کامل، برند، ظرفیت، ردهٔ انرژی و فناوری را فقط از دیتابیس می‌خوانند.
- صفحهٔ محصول در این مرحله فقط اطلاعات، گالری و وضعیت موجودی را نمایش می‌دهد؛ انتخاب تعداد، افزودن به سبد و شمارندهٔ هدر مطابق مرزبندی جدول مراحل به مرحلهٔ هشتم موکول شدند.
- حالت روشن و تاریک فروشگاه از ترجیح سیستم پیروی می‌کند و برای هرکدام تصویر Hero، شیشه، border، نور و سطح مستقل دارد؛ کنترل دستی تم چون در SPEC الزام نشده اضافه نشد.

- مرحلهٔ ششم: Auth.js v5 مطابق سند با `next-auth@5.0.0-beta.32` نصب شد؛ نسخهٔ v5 فعلاً beta است. تنظیمات بدون دیتابیس در `auth.config.ts` و provider در `auth.ts` قرار دارند. wrapper پراکسی نتیجهٔ غیرهمگام lazy Auth.js را await می‌کند.
- صفحات سرور برای رعایت جدول import در AGENTS.md، توابع محافظ را از actionهای احراز هویت فراخوانی می‌کنند؛ این actionها فقط به helperهای سرور واگذار می‌کنند. حساب و ادمین فعلاً فقط نقاط ورود محافظت‌شده و خروج‌اند؛ صفحات کامل آن‌ها متعلق به مراحل ۱۰ و ۱۱ هستند.
- پیام فارسی ۴۰۴ در ریشه لازم است چون `notFound()` در layout ادمین به مرز بالاتر می‌رود؛ این فایل فقط برای شرط دسترسی مرحلهٔ ششم اضافه شد. تم و صفحهٔ اصلی تغییر نکردند.
- ادغام سبد بعد از ورود و ثبت‌نام، طبق جدول مراحل به مرحلهٔ هشتم موکول شد؛ مرحلهٔ ششم هیچ سرویس یا کوکی سبدی اضافه نمی‌کند. نقطهٔ checkout فقط layout محافظ دارد؛ صفحهٔ آن در مرحلهٔ نهم ساخته می‌شود.
- محدودیت تلاش برای ورود و ثبت‌نام، هرکدام پنج درخواست در پانزده دقیقه برای هر IP است. هدرهای IP باید در reverse proxy معتبر بازنویسی شوند؛ بدون IP معتبر از bucket مشترک استفاده می‌شود. قبل از اجرای چند نمونهٔ سرور، store مشترک لازم است.
- آزمون مرورگری از Playwright پایتونِ نصب‌شده بیرون پروژه و Edge استفاده می‌کند؛ این ابزار فقط برای پذیرش واقعی UI و HTTP است و وابستگی جدیدی به برنامه اضافه نمی‌کند.

- مرحلهٔ پنجم: seed با شرط Node یعنی `react-server` اجرا می‌شود تا محافظ‌های `server-only` حفظ شوند. کاربران موجود، شناسهٔ آدرس و هش منطبق حفظ می‌شوند؛ رمز حساب نمونه در صورت تغییر تنظیمات به‌روزرسانی می‌شود. Counter پس از reset خالی می‌ماند و در مرحلهٔ سفارش ایجاد خواهد شد.

- مرحلهٔ چهارم: تعارض نام فایل مدل‌ها در SPEC (`User.ts` و مانند آن) با AGENTS.md به نفع AGENTS.md حل شد؛ فایل‌ها `user.ts`، `category.ts`، `product.ts`، `cart.ts`، `order.ts` و `counter.ts` هستند.
- همهٔ اسکیماها، شامل زیرسندها، timestamps دارند؛ فقط آدرس ذخیره‌شدهٔ کاربر شناسهٔ مستقل دارد. آدرس سفارش و سایر زیرسندهای snapshot شناسهٔ مستقل ندارند. تاریخ DTO به ISO و تمام ObjectIdها به رشته تبدیل می‌شوند؛ `__v` و `passwordHash` بازگشتی حذف می‌شوند.
- رمز ثبت‌نام برای جلوگیری از برش خاموش bcrypt حداکثر ۷۲ بایت است؛ رمز نرمال‌سازی یا trim نمی‌شود. مدل User فقط هش bcrypt با cost 12 می‌پذیرد؛ تولید هش در مراحل seed و احراز هویت انجام می‌شود.
- فیلدهای ناشناختهٔ ورودی حذف می‌شوند: نقش و وضعیت کاربر از ثبت‌نام، soldCount از فرم محصول و مبلغ، مالک و وضعیت پرداخت از ورودی سفارش پذیرفته نمی‌شوند. نامک فرم اختیاری است و تولید/یکتاسازی آن در سرویس مرحلهٔ مربوط انجام می‌شود.
- رشتهٔ خالیِ فیلدهای اختیاری به نبود مقدار تبدیل می‌شود؛ در مدل، مقدار null فیلدهای متنی اختیاری نیز حذف می‌شود تا ایندکس sparse مقدار مشترک خالی نداشته باشد. ارقام فارسی/عربی برای قیمت، تعداد، صفحه، موبایل و کد پستی نرمال می‌شوند و boolean متنی `false` واقعاً false است.
- مقدار اولیهٔ Counter برابر ۱۰۰۰۰۰ است؛ تولید شمارهٔ سفارش و محاسبات مبالغ در مرحلهٔ سفارش پیاده می‌شوند. تغییر سیستم در تاریخچهٔ سفارش می‌تواند `changedBy` نداشته باشد. ترتیب دسته عدد صحیح نامنفی است و URL تصویر فقط http/https پذیرفته می‌شود.
- قواعد نیازمند دادهٔ سایر رکوردها، مانند سطح والد دسته، ممنوعیت حذف دستهٔ دارای محصول و کنترل موجودی سبد، طبق سند در سرویس‌های مراحل مربوط اجرا می‌شوند؛ مرحلهٔ چهارم فقط مدل و اعتبارسنجی ورودی را آماده می‌کند.
- در این محیط دانلود رسمی باینری MongoDB خطای HTTP 403 داد؛ تست مدل‌ها از fallback کانتینر موقت و مستقل استفاده می‌کند. انقضای واقعی TTL با دورهٔ یک‌ثانیه‌ای فقط در سرور تست بررسی می‌شود و تنظیم دیتابیس برنامه تغییر نمی‌کند.

- مرحلهٔ سوم: تنظیمات با `getEnv()` هنگام استفاده در سرور بررسی می‌شوند تا build به اتصال دیتابیس وابسته نباشد؛ تنظیمات seed اختیاری‌اند و در مرحلهٔ seed الزام آن‌ها اعمال خواهد شد.
- برای رعایت قوانین لایه‌ها، health از یک سرویس کوچک استفاده می‌کند. مطابق قرارداد عمومی API در بخش ۸، پاسخ آن `{ data: { status: "ok", db: "up" | "down" } }` با HTTP 200 است؛ `status` سلامت برنامه و `db` وضعیت اتصال را نشان می‌دهد. خطای تنظیمات پاسخ عمومی فارسی با HTTP 500 دارد.
- اتصال اولیهٔ MongoDB حداکثر ۵ ثانیه برای انتخاب سرور منتظر می‌ماند؛ promise مشترک روی `globalThis` نگه داشته می‌شود و پس از شکست اولیه پاک می‌شود تا درخواست بعدی دوباره تلاش کند. اتصال برقرارشده از بازیابی خودکار درایور استفاده می‌کند.
- برای health که Route Handler JSON است، `loading.tsx` و حالت خالی رابط کاربری کاربرد ندارند.

- مرحلهٔ دوم: فقط Button، Input، Card و Badge برای صفحهٔ نمونه لازم‌اند؛ Modal و Pagination در مراحل نیازمند آن‌ها ساخته می‌شوند.
- تاریخ‌ها با منطقهٔ زمانی Asia/Tehran نمایش داده می‌شوند تا نتیجه به منطقهٔ زمانی سرور وابسته نباشد؛ قیمت نامعتبر، منفی یا غیرصحیح با خطای فارسی رد می‌شود.
- slug حروف فارسی را حفظ می‌کند؛ نیم‌فاصله را مانند فاصله و ارقام فارسی/عربی را مانند ارقام انگلیسی در نظر می‌گیرد. عنوان بدون حرف یا رقم به `item` تبدیل می‌شود.
- یکتاسازی slug با `createUniqueSlug(title, exists)` و callback همگام یا ناهمگام انجام می‌شود؛ اتصال دیتابیس ندارد و جایگزین محدودیت یکتایی مدل در مرحلهٔ مربوط نیست.
- صفحهٔ آزمایشی فعلاً در `/` است و ورودی نمونه فقط در مرورگر و با بازنشانی بومی فرم کار می‌کند؛ هیچ داده‌ای در سرور پردازش یا ذخیره نمی‌شود.

- گزینهٔ agentRules در Next.js غیرفعال شد تا اجرای dev محتوای AGENTS.md پروژه را خودکار تغییر ندهد.

- الزام آخرین نسخهٔ پایدار برای TypeScript و ESLint با وابستگی‌های lint ناسازگار شد: typescript-eslint بازهٔ کمتر از 6.1 و eslint-plugin-react نسخهٔ 9 را پشتیبانی می‌کنند. آخرین نسخه‌های سازگار TypeScript 6.0 و ESLint 9 انتخاب شدند تا بررسی‌های اجباری سالم بمانند.
